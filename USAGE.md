# Как пользоваться харнессом

Харнесс — это набор навыков и стандартов для работы с кодом и продуктом. Навыки лежат в `skills/`, стандарты — в `standards/`. Маршрутизатор `AGENTS.md` подсказывает агенту, что загрузить под задачу.

## Структура (треки)

Навыки разбиты по трекам — как в `AGENTS.md` и `skills/_INDEX.md`:

- **Discovery** (что строить — research/оценка/спеки): `am-research`, `am-research-index`, `am-grill-feature`, `am-grill-docs`, `am-pain-mining`, `am-write-specs`, `jtbd`, `grill-plan`, `book/video-knowledge-extraction`.
- **Delivery** (как строить — код): `tdd`, `debugging`, `code-review`.
- **Knowledge-Meta** (слой знаний харнесса): `improve-skill`, `decisions`, `prune`.

Репо устроено так: `skills/` (навыки), `standards/` (конвенции по языкам), `learnings/` + `decisions/` + `state/` (сторы знаний), `scripts/` (инструменты харнесса), `docs/` (спеки/планы). Полная карта структуры — в `README.md`.

## Запустить навык

В Claude Code вызывайте навык слеш-командой — `/am-research`, `/jtbd`, `/am-grill-feature` — или описывайте задачу словами. Маршрутизатор подбирает навык по триггерам в `AGENTS.md`.

Примеры:
- «изучи фичу X», «как работает X» → `am-research`
- «прожарь фичу», «стоит ли делать» → `am-grill-feature`
- «напиши jtbd», «придумай заголовок» → `jtbd`
- «проверь research index», «что устарело» → `am-research-index`

Не грузите всё сразу. Берите только то, что подходит под задачу.

## Внешние навыки (third-party)

Свои навыки линкуются глобально через `link.sh` (в `~/.claude/skills/`, огонь во всех проектах). **Внешние** (чужие) — отдельный случай: они живут в своём клоне-сиблинге и линкуются в **один проект** через `link-nmt.sh`.

Зачем так. Внешние навыки часто сцеплены со своим каноном (читают его по пути от корня проекта) и несут чужую лицензию. Клон-сиблинг = источник правды (`git pull`), а `link-nmt.sh` симлинкует канон + скиллы в корень целевого проекта. Симлинки — не копии: ничего лицензионного не попадает в репозитории харнесса.

Пример — Next Move Theory (Иван Зamesin, AJTBD / NMT):

```bash
# 1. клон-сиблинг (один раз)
cd ~/Documents/Code_projects
git clone --depth 1 https://github.com/zamesin/Next-Move-Theory-Canon-and-Skills.git

# 2. линк в проект (canon + 8 скиллов + контракты → Astra)
bash ~/Documents/Code_projects/agent-knowledge/link-nmt.sh
#   --target <dir>   иной проект
#   --clone  <dir>   иной клон
#   --unlink         снять симлинки

# 3. обновление после апстрима
cd ~/Documents/Code_projects/Next-Move-Theory-Canon-and-Skills && git pull && \
  bash ~/Documents/Code_projects/agent-knowledge/link-nmt.sh
```

Ограничения внешних навыков:

- **Project-local.** `/nmt-*` огонь только в проекте, куда слинковано (канон читается по пути от его корня — запускайте Claude Code из корня проекта).
- **Лицензия.** NMT под CC BY-NC-SA: читайте и применяйте идеи своими словами, **не копируйте** канон в свои репозитории (симлинки — ок, они не копируют). NonCommercial — оцените для коммерческого использования.
- **Gitignore.** Симлинки добавьте в `.gitignore` целевого проекта, чтобы они не въехали в историю (см. `Astra/.gitignore`, секция External methodology).

Где живёт: `link-nmt.sh` — в корне `agent-knowledge/`, рядом с `link.sh`.

## Петля обратной связи

Харнесс учится на каждом запуске. Петля: захват → накопление → улучшение.

```
запуск навыка
   │  [авто] футер: урок → learnings/, строка → state/skill-runs.md
   ▼
накопленные learnings/ + skill-runs.md   ←[человек читает и чистит]
   │  [человек] выбирает навык, запускает improve-skill
   ▼
OIAE: Observe → Inspect → Amend → Evaluate → rollback   [авто внутри запуска]
   │  [человек] сеет evals, разбирает остаток, включает ассершены
   ▼
навык лучше — или откат
```

Что делает само, а где нужен человек:

| Этап | Автоматически | Человек |
|---|---|---|
| Захват урока + строки запуска | футер в конце навыка | — |
| Хранение | `learnings/`, `state/skill-runs.md` (локально) | — |
| Линтер портабельности | `scripts/lint-portability.py` | — |
| Выбор, что улучшать | — | запускает `improve-skill` |
| Петля `improve-skill` | OIAE внутри запуска | — |
| Критерии (evals), разбор остатка | — | сеет и курирует |
| Решения (архитектура, скоуп) | `decisions` пишет и суперседит | принимает решение |
| Чистка памяти | `prune` (P2) | подтверждает удаления |

Коротко: **захват, хранение и саму петлю харнесс делает сам. Человек решает, что улучшать, задаёт критерии и разбирает результат.**

Футер стоит на **11 операционных навыках** (все am-*, debugging, book/video-knowledge-extraction). Без футера: code-review, tdd, jtbd, improve-skill — нет рекуррентных операционных фактов. (Удалены как generic-оверхед 2026-07-21: competitive-analysis, spec-writing, deploy-checklist, incident-response.)

## Улучшить навык (improve-skill)

`improve-skill` — навык, который делает другие навыки лучше. Это **не** то же, что петля обучения: петля копит факты о мире (`learnings/`), а `improve-skill` правит **текст самого навыка** (`SKILL.md`), чтобы его выводы стали качественнее.

Как работает. Для навыка генерятся эвалы (`evals.json` — список проверок). Навык прогоняется на тестовых входах, выходы оцениваются по эвалам. Если проверка падает — агент пишет правило-починку, вставляет в `SKILL.md` и пересчитывает. Стало лучше — коммит; хуже или так же — откат (`git checkout`). Это и есть OIAE: Observe → Inspect → Amend → Evaluate → rollback. Подробно — в `skills/improve-skill/SKILL.md`.

```bash
/improve-skill <skill>            # один навык
/improve-skill <skill> --regen    # пересоздать эвалы (засеять для нового навыка)
/improve-skill --all              # все навыки по очереди
/improve-skill <skill> --dry-run  # только диагноз, без правок
```

Где человек. Человек сеет качество `evals.json` (по критериям самого навыка), запускает `improve-skill`, разбирает оставшиеся провалы и решает, какие предложенные проверки включить. Саму петлю — правит, считает, коммитит или откатывает — навык делает сам.

Зачем нужен. `improve-skill` — двигатель принципа «независимость через эвалы»: эвалы (`evals.json` + `assertion_runner.py`) живут в каждом навыке, а гоняет их `improve-skill`. Без него «харнесс независим от LLM, потому что успех измерим эвалами» — пустые слова.

## Добавить урок вручную

Откройте нужный файл в `learnings/` и допишите блок frontmatter. Формат и правила — в `learnings/README.md`.

```yaml
---
type: operational
key: short-kebab-key
insight: одно предложение, факт без оценки
confidence: 8
source: observed
files: []
ts: 2026-06-18
scope: harness
---
```

Пишите то, что сэкономит 5+ минут в следующий раз. Не пишите очевидное и разовые ошибки.

## Посмотреть, что накопилось

- `learnings/patterns.md`, `pitfalls.md`, `preferences.md`, `operational.md` — уроки по типам.
- `state/skill-runs.md` — журнал запусков: что используется, что падает, что мертво.

## Решения

Архитектурные решения, скоуп, выбор инструмента — в `decisions/decisions.active.md`. Это отдельный стор: не уроки и не заметки о пользователе, а зафиксированное решение с причиной.

Записать или найти — навык `decisions` (`log` / `search` / `supersede`). Решение не переподнимают молча: отменили — суперседят (новое активное + пометка старого). Формат — в `decisions/README.md`.

## Инструменты — по возможности, не по имени

В текстах навыков инструмент называют возможностью, а не внутренним именем. Конкретные имена живут в `AGENTS.md`, раздел «Tool registry». Пишите «возможность jira», а не `mcp__jira__get_issue`. Это держит харнесс независимым от конкретного агента и LLM.

Проверка:

```bash
python3 scripts/lint-portability.py skills
```

Ноль находок — норма. Есть находки — замените имя на возможность.

## Поддержка (governance)

Сторы растут. Три механизма держат их в порядке — и ни один не грузит файлы целиком.

**Чистка.** `prune` находит устаревшие записи (ссылаются на удалённые файлы) и конфликтные (один `key` — разные `insight`) в `learnings/` и `decisions/`. Режим `check` — только отчёт; `prune` — спрашивает по каждой: удалить / оставить / обновить. Возраст сам по себе никогда не флагует — только изменение. Единый зонтик чистоты — навык `am-docs-audit`: аудирует док-слой мета-репо Astra против ownership-секции в `AGENTS.md` и затем запускает `prune` (сторты). Один вход «почисти весь харнес».

**Ротация телеметрии.** `state/skill-runs.md` растёт быстрее всех. Периодически:

```bash
./scripts/rotate-skill-runs.sh 500   # оставить последние 500 строк, остальное — в архив
```

**Выборочное чтение.** Главное правило: **сторы никогда не грузятся целиком.** `scripts/auto-retrieve.py "<тема>"` возвращает ≤3 релевантных урока; `am-research` зовёт его в начале работы. Так рост файлов не засоряет контекст.

**Регрессионные эвалы.** Живут в каждом навыке — `evals.json` + `assertion_runner.py`, генерируются и гоняются навыком `improve-skill` (как — см. «Улучшить навык» выше). Засеять для нового навыка: `/improve-skill <skill> --regen`. Отдельной параллельной системы эвалов нет — чтобы не дублировать.

## Что где лежит

| Нужно | Куда смотреть |
|---|---|
| Узнать, какой навык грузить | `AGENTS.md` |
| Какой возможностью звать инструмент | `AGENTS.md` → Tool registry |
| Стандарт по языку или инструменту | `standards/<category>/_INDEX.md` |
| Операционные уроки | `learnings/` |
| Журнал запусков | `state/skill-runs.md` |
| Принятые решения | `decisions/decisions.active.md` |
| Спецификация и план развития харнесса | `docs/superpowers/specs/`, `docs/superpowers/plans/` |

## Развитие

Харнесс развивается фазами. Сделано: **P0** (захват, телеметрия, футер, tool-registry, линтер) → **P1** (стор решений `decisions`, OIAE-маппинг `improve-skill`) → **P2** (governance: `prune`, выборочный `auto-retrieve`, ротация) → **роллаут** футера на 11 операционных навыков. Спецификация и планы — в `docs/superpowers/specs/`, `docs/superpowers/plans/`. Возможное дальше: decay для preferences, авто-подгрузка решений по теме, CI-хук на линтер.
