# Taxonomy — «Вид работ» и «Специализированная разработка»

Канон: Confluence `DRSTAND`, pageId **322803823** «Вид работ в задачах продуктовых проектов».
Поля Jira: **«Вид работ»** = `customfield_22202`; **«Специализированная разработка»** = `customfield_33800`.

## Governing lens: CAPEX или OPEX

Каждая задача — это сначала ответ: **труд капитализируется в актив продукта (CAPEX) или списывается в расход периода (OPEX)?** Потом уточняешь конкретное значение.

- **CAPEX** (создаёт/улучшает долгосрочный актив продукта): **Develop Roadmap, Certification**.
- **OPEX** (текущая деятельность, поддержка, работа под конкретного заказчика): **Installation, Business Research, Custom Develop, Internal, Support**.

## «Вид работ» (customfield_22202) — 7 значений

| Значение | C/O | Что считать этим | Решающий сигнал |
|---|---|---|---|
| **Develop Roadmap** | CAPEX | Всё, что идёт в релиз продукта по роадмапу: новая фича, доработка существующей, **обоснованный** техдолг/рефакторинг **для всех** заказчиков. Включает анализ, ТЗ, разработку, конфигурацию, тестирование, продуктовые доки. | результат попадает в релиз продукта; пользу получают все заказчики |
| **Installation** | OPEX | Сборка программно-аппаратных комплексов (ПАК). | физическая сборка железа + ПО под конкретный экземпляр |
| **Business Research** | OPEX | Исследования рынка, ёмкость, конкуренты, проверка гипотез. Не связано с разработкой напрямую. | исследовательская задача, кода в релизе нет |
| **Custom Develop** | OPEX | Доработка/рефакторинг/багфикс **под конкретного заказчика или контракт**. | привязка к заказчику/контракту; результат НЕ в общем релизе |
| **Internal** | OPEX | Внутренние работы: процессы, онбординг, найм, **CI/CD и автоматизация**, девопс, внутренние коммуникации, обучение. Проект LIFE — весь Internal по умолчанию. | не реализует пункт роадмапа; обслуживает команду/инфру |
| **Certification** | CAPEX | Работа под регулятора (ФСТЭК / МО / РБПО / RFAL и др.) + доки к сертификации: доработки по требованиям регулятора, подготовка/правка документации, отработка замечаний. | драйвер — требование регулятора / получение сертификата |
| **Support** | OPEX | Техподдержка 1-2-3 линия: консультации и сопровождение продаж или использования ПО (в тестовой/прод-среде заказчика). | задача из контура техподдержки/саппорта |

## Правила разрешения споров (здесь рождаются «сомнительные»)

1. **Техдолг / рефакторинг / багфикс** — главный развилок:
   - результат идёт в **общий релиз**, пользу получают **все** заказчики → **Develop Roadmap** (CAPEX);
   - сделано **под конкретного заказчика/контракт**, в общий релиз не попадает → **Custom Develop** (OPEX);
   - в тикете не указано «для всех»/«под заказчика» и это не выводимо → **сомнительная** (ручная разметка).
2. **CI/CD, тестовая инфраструктура, автоматизация, девопс** → **Internal** (НЕ Roadmap), даже если косвенно помогает релизу. Частая ошибка — тащить в Roadmap.
3. **Работа под регулятора** (ФСТЭК и т.п.) → **Certification**, даже если это разработка/доработка. Драйвер — сертификат, а не роадмап.
4. **Тестирование / QA**: тесты по фиче роадмапа → **Develop Roadmap** (тестирование — этап роадмапа); стабилизация/инфра тестов, тестовые стенды, автотесты-обвязка → **Internal**. Если не различить — сомнительная.
5. **Документация**: продуктовая/сопроводительная, идущая в релиз → **Develop Roadmap**; под сертификацию → **Certification**; внутренняя (инструкции команде, онбординг, процессы) → **Internal**.
6. **Исследование без кода** → **Business Research**; исследование, плавно перешедшее в разработку фичи, идущей в релиз → **Develop Roadmap**.

## Решения команды (Astra Monitoring, 2026-07-23)

Эти два правила — явная позиция команды по развилкам, где канон допускает трактовки:

- **Дженерик-багфикс продукта** (тип «Ошибка» / баг без привязки к заказчику), идущий в релиз → **Develop Roadmap** (CAPEX). Фикс улучшает продукт для всех.
- **Тестирование / QA** — включая стабилизацию тестов, тестовую инфру и тестовую документацию продукта → **Develop Roadmap** (CAPEX). Тестирование = этап роадмапа.
  - Исключение: **чистый CI/CD-пайплайн и девопс, НЕ связанный с тестированием** → **Internal** (OPEX).
- **amctl** (CLI-инструмент продукта Astra Monitoring) → «Специализированная разработка» = **AI-Ready** (не «Не проводилась»).
- **Планирование / обсуждение** («обсудить план…», «спланировать») → **Internal** (коммуникация/процесс, не само тестирование или разработка), даже с тегом `[Test]`. Само тестирование → Develop Roadmap.

## Префиксы `[Front]` / `[Back]` / `[Test]` / `[Infra]` — это команда/компонент, НЕ вид работ

Не классифицируй по префиксу. Как подсказка (не правило):
- `[Infra]` / `[DevOps]` часто → **Internal**;
- `[Front]` / `[Back]` → обычно **Develop Roadmap** или **Custom Develop** (решает суть, не префикс);
- `[Test]` → зависит (см. правило 4).

## «Специализированная разработка» (customfield_33800)

> ⚠ **На MON поле не подключено** — не пишется (400 на любое значение). **Не записываем.** Классификацию сохраняем в артефакте на будущее; запись возможна только после подключения поля к проекту через портал обращений Astra Linux (по канону DRSTAND-322803823).

Ортогональное поле: помечает, касалась ли работа одной из специализированных «готовностей». По умолчанию **«Не проводилась»**.

| Значение | Когда ставить |
|---|---|
| **Не проводилась** | работа не связана с готовностями ниже (большинство тикетов) |
| **Cloud Ready** | задача про готовность к облаку: Astra Cloud, гибридные среды, адаптация под облако (часто кубернетес/облачная интеграция) |
| **Security-Ready (ИБ)** | соответствие стандартам ИБ, харденинг, защита |
| **AI-Ready** | поддержка ИИ-технологий |
| **Platform-Ready** | совместимость с экосистемой компании |

Правило из канона: если **вся** задача про одну готовность — поле задачи = эта готовность (наследуется в Tempo автоматически). Если готовность — лишь **часть** задачи — в поле задачи «Не проводилась», в Tempo выбирается вручную. Для нашего прогона: ставь доминирующую готовность, иначе «Не проводилась».

> ⚠ Перед массовой записью этого поля верифицируй, что целевой проект принимает именно эти option-строки (см. шаг 2 в `SKILL.md`). На MON подтверждённых примеров мало.

## Порог «сомнительных» — стандартный

Тикет уходит в ручную разметку, если:
- два значения подходят **равноценно** — нет решающего сигнала;
- **мало данных** в тикете: пустое описание, нет Epic, нет коммитов;
- техдолг/рефакторинг/багфикс **без указания «для всех» / «под заказчика»**;
- регуляторная работа vs роадмапная — не различить;
- `confidence` ниже ~0.7.

В артефакт по каждому: кликабельная ссылка на тикет, тип, статус, Epic, лучшая догадка (предсказание), причина сомнения.
