## Фаза 0: Prerequisite Gate

### Матрица читаемости форматов

| Формат | Агент читает напрямую? | Что нужно |
|--------|----------------------|-----------|
| **epub** | Да | `unzip` — распаковать HTML-файлы, читать их |
| **fb2 (UTF-8)** | Да | Ничего — XML с текстом в `<p>` тегах |
| **fb2 (win-1251)** | Да, после iconv | `iconv -f windows-1251 -t utf-8 file.fb2` |
| **HTML** | Да | Ничего |
| **markdown** | Да | Ничего |
| **txt** | Да | Ничего |
| **docx** | Практически нет | `unzip -p file.docx word/document.xml` — 10:1 шум:сигнал, лучше pandoc |
| **rtf** | Нет | `textutil -convert txt` (macOS) или pandoc |
| **doc (OLE2)** | Нет | antiword / libreoffice |
| **pdf** | Нет | `pdftotext` (poppler) текстовый / `ocrmypdf` сканы |
| **mobi** | Нет | calibre `ebook-convert` |

### Логика принятия решения

1. Формат в зелёной зоне (epub, fb2, HTML, md, txt) — читаем напрямую, конвертация не нужна и часто **вредит** качеству
2. Формат в жёлтой зоне (fb2 win-1251) — одна команда iconv, затем читаем
3. Формат в красной зоне (docx, rtf, doc, pdf, mobi) — → `references/conversion-guide.md`, затем вернитесь сюда. **Для PDF** структура глав часто теряется при извлечении текста — до fan-out проверьте bookmarks/TOC (см. conversion-guide → «Восстановление структуры глав PDF»).

### Доступность инструментов

Перед использованием проверьте, что нужные инструменты установлены — это экономит поздние падения в красной зоне:

```bash
for t in unzip iconv pandoc antiword libreoffice tesseract calibre pdftotext ocrmypdf; do
  command -v "$t" >/dev/null 2>&1 || echo "ОТСУТСТВУЕТ: $t"
done
```
Отсутствующий инструмент для красной зоны → установить (`references/conversion-guide.md` → «Установка инструментов») либо предупредить пользователя. Зелёная зона требует только `unzip`/`iconv`.

**Epub: консолидация (не конвертация).** HTML внутри epub может быть разбит на 30+ файлов. Для чтения агентом — объединить в порядке **spine** в один файл. Это `cat` в правильном порядке, не pandoc.

Порядок чтения — **spine** в `content.opf`, а **не** `toc.ncx`. `toc.ncx` — это оглавление-навигация, оно может не совпадать с реальным порядком и полнотой глав. Spine — источник истины.

```bash
unzip -o book.epub -d book_epub/
OPF=$(find book_epub -name "*.opf" | head -1)   # обычно content.opf
# Порядок idref'ов из <spine> (в порядке появления):
sed -n 's/.*<itemref[^>]*idref="\([^"]*\)".*/\1/p' "$OPF"
# затем каждый idref → href из <manifest>, и cat href'ов в этом порядке
```

**Epub/fb2: изображения.** Извлечь из архива в `images/` с осмысленными именами (не `00003.png`, а `technology-adoption-life-cycle.png`). Изображения диаграмм — часть аргументации автора, могут использоваться в документе знаний.

**Почему конвертация вредит:** pandoc/calibre из epub генерируют CSS-артефакты (`{.calibreXX}`, `:::` div-обёртки), ломают пути к изображениям, загрязняют заголовки. Исходный HTML внутри epub — чище, чем сконвертированный markdown.

## Orchestration: чтение длинных книг

Книга — это десятки–сотни тысяч слов. Один агент не может прочитать книгу целиком **и** извлечь знания по всем категориям, не переполнив контекст. Workflow ниже по умолчанию разделяет **чтение** и **синтез**.

### Порог fan-out

Если книга **> 8 глав** ИЛИ **> ~40 000 слов** (`wc -w` по склеенному тексту) — обязательно fan-out:

1. **Читатель на главу (subagent).** Один subagent на главу (или батч глав) читает только свою порцию и пишет локальный артефакт `chapters/chapter_NN.md` по шаблону «Глава как аргумент» (Structure B) или категорийный чанк (Structure A). Глава изолирована — контекст не копится, сколько бы глав ни было. На каждую единицу вешайте **тег темы из canonical словаря** (см. «Словарь тем» ниже) — он нужен синтезатору для детерминированной дедупликации кросс-batch (без общего словаря дедуп становится угадывательным).
2. **Синтезатор (отдельный агент).** Читает **только** готовые `chapters/*.md` (не саму книгу), собирает финальный knowledge-документ и тянет нарративную дугу + межглавные связи. Книгу целиком синтезатор НЕ перечитывает — это задача читателей. **Дедуп по тегам темы** (`#…`): единицы с одинаковым тегом из разных батчей сливайте в одну (единый ID), но **сохраняйте ВСЕ уникальные якорные цитаты** из сливаемых единиц — не выбирайте одну, иначе теряется grounding.

Это гарантия двух вещей: контекст не переполняется на любой длине книги, и итоговый документ собирается из уже записанных блоков, а не генерируется одним заходом (защита от truncation-цикла).

### Словарь тем (theme vocabulary)

Тег темы (`#…`) — deterministic-якорь дедупа **только если все reader-агенты используют один словарь тем**. Если каждый придумывает теги независимо — гранулярность расходится (один ставит `#стоп-слова`, другой `#лексика` на ту же тему), и синтезатор возвращается к угадывательному дедупу по смыслу. Поэтому словарь тем строится **первым шагом fan-out**, до запуска readers:

1. **Источник тем — структура книги.** Извлеките темы из оглавления/глав/разделов: epub — названия глав из spine (`<h1>`/`<title>` каждого xhtml); PDF — bookmarks или восстановленный TOC (см. conversion-guide); иначе — заголовки чанков. Авторское членение и есть canonical.
2. **Канонические слаги.** Каждой теме — короткий слаг на языке книги (`#контекст`, `#примеры`, `#сюжет`). Сверните синонимы и падежи в один слаг.
3. **Раздайте словарь readers.** Каждый reader обязан вешать тег **из этого словаря**. Тема в порции не покрыта словарём — reader добавляет её как `#имя(?)` с пометкой `(?)`.
4. **Синтезатор дедупит по canonical тегам.** Одинаковый canonical тег из разных батчей → слить (с сохранением всех уникальных цитат). `(?)`-теги нормализовать: встретились в ≥2 батчах → сделать canonical; в одном → оставить как есть.

### Маленькие книги

Если книга ≤ 8 глав и ≤ ~40 000 слов — допустим single-pass одним агентом, но финальный документ всё равно собирай из поэтапно записанных блоков, не одним `Write`.

### Промежуточные артефакты

Все промежуточные записи subagents складывай в папку книги: `{book-title}/chapters/chapter_NN.md`, `narrative-arc.md`. Финальный `{book-title}_knowledge.md` собирается из них последним шагом (Фаза 3). Не держи главы только в памяти — пиши на диск после каждой.

### Санитизация чанка перед извлечением

Прежде чем извлекать знания, очистите чанк от шума — иначе он попадёт в вывод как контент:
- **Вырезайте:** URL-ссылки, колонтитулы, вклеенные оглавления (TOC, появляющийся внутри body), врезки «Видеоурок»/«См. также»/«Ещё по теме», нумерацию страниц, пустые обёртки.
- **Справочные перечни** (списки стоп-слов на 500 строк, словари канцеляризмов) — это справочный аппарат, а не извлекаемые единицы. Не извлекайте каждое слово; если важно — сошлитесь на перечень целиком («автор приводит ~500 стоп-слов; ключевые: …»).
- **Таблицы «Было/Стало»** на PDF часто рассыпаются в линейный текст — восстанавливайте пары по структуре, если не выходит — фиксируйте потерю в «сломанных местах».
- **PDF-структура:** если книга из PDF и границы глав потеряны (чанки нарезаны по страницам) — декларируйте это в метаданных (`Охват: постранично, структура глав не восстановлена`), не маскируйте.

### Integrity-чек fan-out

Fan-out хрупок: один reader может «отчитаться», не дописав файл, и синтезатор тихо деградирует — молча проигнорирует пропущенный батч или подставит артефакт прошлой итерации (так теряются целые разделы книги без сигнала). Чтобы исключить тихую потерю:

- **Reader (после записи):** верифицируйте, что batch-файл реально на диске и непуст. Не возвращайте сводку «готово», пока непустой файл не записан; если запись не подтвердилась — повторите.
- **Синтезатор (перед сборкой):** проверьте, что **все** ожидаемые `batch_*.md` присутствуют и непусты. Если батч отсутствует или пуст — **СТОП с явной ошибкой** («отсутствует batch_A.md — синтез прерван, перезапустите reader A»). НЕ подставляйте пропуски молча и НЕ берите артефакты прошлой итерации без явной пометки в метаданных.

## Фаза 1: Первичное чтение

### 1.1 Анализ структуры

- Прочитать оглавление (если есть)
- Определить основные разделы и главы
- Выделить ключевые темы каждой главы

**Для fb2:** метаданные уже внутри файла — извлечь из `<title-info>`: автор, название, жанр, аннотация, язык, год издания. Не вводить вручную то, что уже структурировано.

**Для epub:** метаданные — в `content.opf`, названия глав (оглавление) — в `toc.ncx`, **порядок сборки глав** — spine в `content.opf` (см. Фазу 0). `toc.ncx` — навигация, не источник порядка.

```markdown
# Структура книги: [Название]

## Часть 1: [Название]
- Глава 1: [Тема]
- Глава 2: [Тема]
```

### 1.2 Классификация типа книги

Определите тип по двум осям — это определяет, на чём фокусироваться при извлечении.

**Ось 1: Предметная область**
Technology / Production / Marketing / Management / Psychology / Finance / Other

**Ось 2: Режим аргументации**

| Режим | Описание | Что выделять |
|-------|----------|--------------|
| **New model** | Автор предлагает новый фреймворк | Кросс-главные модели, компоненты, применимость |
| **Refutation** | Автор атакует существующую парадигму | Что опровергается, контринтуитивные инсайты, альтернатива |
| **Methodology** | Автор даёт пошаговую систему | Процессы, техники, инструменты, условия применения |
| **Narrative** | Автор рассказывает историю для доказательства точки | Сюжет, ключевые повороты, lessons learned |

Результат классификации записывается в метаданные документа знаний.

### 1.3 Восстановление нарративной дуги

**Цель:** Понять логику авторской мысли — не ЧТО сказано, а ПОЧЕМУ именно в этом порядке.

- Для каждой главы сформулировать one-sentence summary: "Глава N показывает, что..."
- Определить главный тезис главы — единственную мысль, без которой глава теряет смысл
- Определить ПОЧЕМУ эта глава идёт после предыдущей
- Определить какое вопрос/напряжение глава разрешает и какое новое создаёт

Формат — см. `references/templates.md` (Нарративная дуга).

### 1.4 Выделение ключевых концепций

- Выписать авторские термины и определения (не общеупотребительные — только концепции автора)
- Выделить ключевые модели и фреймворки (часто появляются в нескольких главах)
- Отметить важные цитаты и формулировки

## Фаза 2: Извлечение знаний

### 2.1 Категории извлекаемых знаний

| Категория | Что извлекать |
|-----------|---------------|
| **Главные идеи** | Ключевые мысли и выводы автора, центральные концепции |
| **Проблемы** | Что решает книга, что описывает, что возникает при применении |
| **Предпосылки** | Явные и неявные предположения автора, условия применимости |
| **Последствия** | Результаты применения, влияние на практику |
| **Методология** | Пошаговые процессы, методы, техники, инструменты |
| **Инсайты** | Неожиданные открытия, контринтуитивные идеи, озарения |

**Опциональные категории** (добавлять, если книга их даёт — типично для прикладных/методических книг):

| Категория | Что извлекать |
|-----------|---------------|
| **Patterns / Recipes** | Жанровые приёмы, тактики, готовые формулировки и шаблоны («заголовок-антипример», «статья для новичков»). Самый густой слой у прикладных книг |
| **Антипаттерны** | Что НЕ делать, типовые ошибки, контрпримеры |

**Правила категоризации:**
- **Мульти-категориальность.** Реальная единица часто принадлежит нескольким категориям сразу (формула = идея + методология; кейс = методология + инсайт). Не плодите дубли — одна единица имеет **единый ID**, первичную категорию и список вторичных: `«Эффективность vs правота» [Идея; Инсайт; Предпосылка]`.
- **Категории зависят от режима книги.** Для Methodology/New model «Предпосылки» часто пусты — автор работает индуктивно и не формулирует assumptions явно. Допустимо восстановить их из оговорок с пометкой `[интерпретация]` или оставить категорию пустой. Не нагнетайте пустоту ради заполнения.
- **Patterns/Антипаттерны — часто вторичная категория.** Конкретный приём (заголовок-антипример) одновременно является идеей и Pattern. Не создавайте дубль-единицу: помечайте Pattern как вторичную категорию к основной (`[Идея; Pattern]`), а не отдельную запись. Отдельная Patterns-запись — только когда приём самостоятелен (не сводим к идее/методологии).
- **Мета-уровень.** В книгах о коммуникации/письме/методе автор иногда рефлексирует о конструкции самой книги («пример о примерах», «эта глава построена так, чтобы…»). Помечайте такие единицы `[мета-уровень]` — они относятся к устройству книги, а не к её предмету; не смешивайте с предметными идеями.

### 2.2 Cognitive Quality (Когнитивное качество)

Каждое извлечённое знание проверяется по пяти принципам:

**Принцип 1: Контекст и Применимость**
Знание не существует в вакууме. Для каждой идеи определите границы применимости:
- Целевая аудитория: Novice / Pro
- Состояние читателя: Crisis / Growth / Stacking
- Цель потребления: Solve / Learn / Confirm

**Принцип 2: Типология Пользы (Utility Taxonomy)**
- **Функциональная:** Улучшает процесс, экономит ресурсы
- **Социальная:** Повышает статус, авторитет, аргументацию
- **Психологическая:** Снижает тревогу, даёт уверенность, развлекает
- **Нормативная / Ethical:** Меняет понимание долга/ответственности («ясность = ответственность, а не нейтральная истина») — типична для книг о коммуникации, этике, пропаганде

Если автор вводит **свою** типологию пользы (часто у методологов) — используйте её с пометкой `[по автору: ...]`, не подгоняйте под этот список.

**Принцип 3: Синтаксис Действия (Actionable Syntax)**
- Тест на визуализацию: Можно ли изобразить концепт как сцену?
- Грамматика: Субъект + Глагол + Объект. Избегать абстракций ("Оптимизация") в пользу действий ("Директор сокращает")
- Приземление: Абстрактные принципы должны иметь конкретные примеры (Case Studies)

**Принцип 4: Armament Test**
Можно ли использовать это знание как аргумент в дискуссии? Если знание нельзя превратить в убедительный аргумент без книги — оно недостаточно конкретно. Банальности ("надо планировать") не проходят этот тест.

Нюансы:
- Банальность оценивается для **целевой аудитории единицы** (Novice/Pro из Принципа 1): «правило абзацев» тривиально для профи, но ценно для новичка. Указывайте аудиторию, при которой единица проходит тест.
- «Банальность + нетривиальное условие применимости» проходит: «планируйте — но только если горизонт больше N, иначе планирование дороже ошибки».

**Принцип 5: Укоренённость (Groundedness)**
Каждое интерпретативное утверждение — главный тезис, ключевой инсайт, «что автор опровергает», «какое напряжение создаёт» — должно быть **заякорено** в тексте книги. Два варианта:
- Прямая якорная цитата рядом с утверждением (короткая, со ссылкой на главу/страницу); либо
- Явная пометка `[интерпретация]`, если это ваш вывод, которого в тексте нет буквально.

Нюансы:
- Для **составного** утверждения (тезис собран из 2–3 мест в тексте) разрешите 2–3 короткие цитаты вместо одной.
- Различайте **цитату-факт** и **цитату-оценку/гиперболу**. Триггер `[оценка автора]`: любые числа/проценты/«в N раз»/«большинство»/«всегда», которые автор не подтверждает источником и вы не можете верифицировать — это авторская риторика, не факт. Помечайте `[оценка автора]`.
- **Маркер `[интерпретация]` обязателен до финального документа.** При fan-out синтезатор НЕ имеет права «очищать» его — читатель финала должен видеть, где реконструкция. Мешает формату — выносите в сноску/колонку, но сохраняйте.

Принципы 1–4 проверяют *форму* знания (применимо, полезно, действенно, аргументативно). Этот проверяет его *достоверность* — разделяет «автор это сказал» и «я так вывел». Без якоря знание рискует оказаться галлюцинацией, вооружиться которой опаснее, чем не знать вовсе.

### 2.3 Шаблон извлечения по категориям

Формат для каждой извлечённой единицы знания — см. `references/templates.md` (Формат извлечения знаний по категориям).

Процесс для каждой категории:

1. **Главные идеи:** Прочитать каждую главу → выделить 1-3 главные идеи → записать в формате шаблона → проверить связь между главами
2. **Проблемы:** Выделить проблемы, которые решает/описывает книга → записать с контекстом и решениями
3. **Предпосылки:** Выделить явные и неявные предположения автора → определить условия применимости → записать с контекстом
4. **Последствия:** Выделить описанные и потенциальные последствия → записать с контекстом
5. **Методология:** Выделить пошаговые процессы, методы, инструменты → записать в формате инструкций
6. **Инсайты:** Выделить неожиданные и контринтуитивные идеи → записать с контекстом и применением

### 2.4 Шаблон «Глава как аргумент»

**Применяется когда:** Режим аргументации = New model / Refutation / Narrative (когда автор выстраивает связный аргумент от главы к главе). В этом режиме единица извлечения — **глава**, а не тип знания.

Полный шаблон со всеми полями и пошаговый процесс извлечения — `references/templates.md` (Шаблон «Глава как аргумент»).

## Фаза 3: Структурирование знаний

### 3.1 Выбор структуры

**Структура A: Каталог знаний** — для справочников, энциклопедий, наборов независимых тем. Нет связного аргумента от главы к главе. Полный шаблон → `references/templates.md`.

**Структура B: Понимание книги** — для narrative-driven книг (business/strategy/научно-популярные), где автор выстраивает связный аргумент. Полный шаблон → `references/templates.md`.

Структура B включает:
- Метаданные — markdown-разделом, не YAML (автор/соавторы, год, издатель/ISBN, тип, режим, формат источника, структура-примечание). См. `references/templates.md` → «Формат метаданных».
- **О чём книга и кому читать** (front-loaded verdict) — суть, кому читать, что уникального, вердикт. Чтобы человек решил за первый экран, без чтения всей базы.
- Словарь концепций автора (до глав — без него теряется смысл)
- Ключевые модели и фреймворки (кросс-главные модели)
- Нарративная дуга
- Главы как аргумент (по шаблону 2.4)
- Карта инсайтов (без искусственных лимитов — столько, сколько книга даёт)
- Методология в действии
- **Единицы знаний** (идеи/инсайты/методы/patterns/антипаттерны): каждая со **стабильным ID** (`K-001` / `IDEA-001`), читается как проза (не анкета подсекций), canonical-тег — compact-меткой, группировка по темам/главам (не по `#тегам`). **batch-internal ID — в Provenance, не в тело.** См. `references/templates.md` → «Формат извлечения знаний по категориям».
- Provenance (в конец документа) — как собран документ: дата, canonical-темы, батчи, дедуп, охват чанков, **ID-mapping (стабильный ← batch-ID)**. Не в шапку.

### 3.2 Структура библиотеки (для сценария 3)

**Правила именования:**
- Название папки и файлов — на языке оригинала книги (не транслитерация, не перевод)
- Автор указывается в имени папки
- Формат: `{author-last-name}/{book-title}/` — иерархия по автору
- Один файл знаний на книгу: `{book-title}_knowledge.md`. Историю изменений ведёт git, не номера версий в имени файла

```
knowledge-base/
└── books/
    ├── moore/
    │   └── inside-the-tornado/
    │       ├── source/                        # Архив оригинала
    │       │   └── inside-the-tornado.epub    # Исходный формат (не конвертировать)
    │       ├── inside-the-tornado.md          # Конвертированный текст (если нужен)
    │       ├── inside-the-tornado_knowledge.md # Извлечённые знания
    │       └── images/                        # Изображения из книги
    └── reicht/
        └── thinking-fast-and-slow/
            ├── source/
            │   └── thinking-fast-and-slow.epub
            └── thinking-fast-and-slow_knowledge.md
```

**Почему так:**
- `source/` хранит оригинал для повторного извлечения, перепроверки, или смены шаблона
- Иерархия по автору — стандарт библиотечной практики, упрощает навигацию при росте базы
- Название на языке оригинала — чтобы поиск по содержимому совпадал с названием папки
- Нет `index.md` — при структуре `author/title/` навигация через файловую систему. Поиск — `grep -r "pattern" knowledge-base/books/`
