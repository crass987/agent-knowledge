# Вёрстка в Markdown — чтобы текст сканировался

`../archive/presentation.md` описывает подачу для журнала и лендинга: модули, плашки,
иллюстрации, абзацы на развороте. Здесь — конкретика для Markdown: как
расставить заголовки, когда взять список, а когда абзац или таблицу, как не
получить «стену текста» или «списочную простыню».

Вёрстка решает сверхзадачу архитектуры (см. `architecture.md`): ключевые мысли
должны быть видны по диагонали за пять секунд — до того как читатель решил
читать. Слова могут быть безупречны, но если они лежат монолитным блоком,
читатель до них не доберётся.

## Иерархия заголовков

- **Один `H1` на документ** — заголовок документа. Остальные секции начинаются
  с `H2` и глубже. Так навигация и якоря работают предсказуемо.
- **Уникальные полные имена.** Не «Итоги» в каждой секции, а «Итоги анализа» и
  «Итоги интервью». Из заголовков строятся якоря и оглавление — одинаковые
  имена их ломают.
- **Информативные, не метки.** «Что сломалось 14 мая и как починили» — хорошо.
  «Информация об инциденте» — мусор. Это правило дублирует `../archive/presentation.md`,
  но для Markdown оно критично: подзаголовок — это навигация.

Перед заголовком и после — пустая строка. Без неё парсер может склеить заголовок
с предыдущим абзацем.

## Когда список, когда абзац, когда таблица

Это главный выбор вёрстки, и решает его форма данных, не настроение автора.

| Ситуация | Формат | Почему |
|---|---|---|
| 1–3 однородных элемента | **Проза** | Список из двух пунктов — шум |
| >3 элементов с повторяющейся структурой | **Список** | Каждый виден, легко сканировать |
| >8–10 элементов | **Таблица или группы** | Длинный список пугает |
| Две оси сравнения (признак × объект) | **Таблица** | Проза или список скроют параллели |
| Идеи развивают друг друга | **Проза** | Список убивает связность |
| >2 списков подряд | **Разбить прозой** | Иначе «списочная простыня» |

Список — инструмент, не значение по умолчанию. Он хорош для независимых
равнозначных пунктов. Там, где мысль течёт от одного к другому, список
разрывает её на обрубки — пишите прозу.

Таблица — для однородных данных по двум осям. Если в колонке все значения
одинаковые или половина ячеек пуста — данные не табличные, переводите в список.

## Списки — механика

- **Обобщающий ключ.** Перед списком — предложение, которое объясняет, что в
  нём. Не «Особенности:», а «Метрика состоит из трёх частей:». Это дублирует
  `hygiene.md` проход 7, но для Markdown обязательно: без ключа пункт «лёгкая
  овощная закуска» висит в воздухе.
- **Одинаковая структура пунктов.** Все начинаются с той же части речи,
  примерно той же длины. Смесь из «Удобный интерфейс» и «Также мы добавили
  возможность экспорта, который раньше был только в Enterprise» — сбой.
- **Пункт — не абзац.** Если пункт разросся до пяти строк — это абзац, а не
  пункт списка. Вынесите в прозу под подзаголовком.
- **Lazy numbering для длинных списков.** Нумеруйте как `1. 1. 1.` — тогда
  вставка нового пункта не собьёт номера рендера. Для короткого финального
  списка можно `1. 2. 3.` (приятнее в исходнике).

Вложенность — один уровень обычно хватает. Два — максимум. Три уровня списка
читатель уже не парсит.

## Код

- **Fenced-блоки с языком**, не отступы в четыре пробела: ` ```python `,
  ` ```bash `. Так подсветка работает, а границы блока однозначны.
- **Inline-код в бэктиках** для имён полей, файлов, команд, путей:
  `README.md`, поле `user_id`. Не для выделения — для кодовых сущностей.
- **Код внутри списка** — отбейте блок отступом, иначе он ломает нумерацию.

## Ссылки

- **Информативный текст.** Не «подробнее [здесь](url)» и не дублирование URL.
  Вплетайте ссылку в смысл: «[гайд по Markdown](url) описывает…».
- **Длинные ссылки — reference-style** в таблицах, чтобы ячейки не расползались.
- **Якоря** строятся из заголовков — потому те и должны быть уникальными.

## Markdown вместо HTML

HTML-вставки (`<div>`, `<br>`, атрибуты) ломают переносимость: исходник
перестаёт читаться как простой текст, рендереры ведут себя по-разному. Если без
HTML не обойтись — скорее всего, вы решаете не ту задачу. Markdown покрывает
почти всё; большие сложные таблицы — единственный частый повод для отступления.

## Антипаттерны

| Провал | Признак | Лекарство |
|---|---|---|
| Стена текста | Абзац в полстраницы без подзаголовка | Дробить; подзаголовок «в подбор» ключом |
| Списочная простыня | Пять списков подряд, прозы нет | Часть списков — в прозу |
| Список-абзац | Пункт списка на 5–8 строк | Вынести в отдельный абзац под подзаголовком |
| Таблица не к месту | Колонка с одним значением, пустые ячейки | Перевести в список |
| Журнал правок в тексте | «(правка 2026-07-07: …)» — мета о редактуре | Убрать; история — в git |
| Заголовок-метка | «Введение», «Итоги», «Прочее» | Назвать суть раздела |

## Чек-лист вёрстки

- [ ] Один `H1`; секции с `H2`; заголовки уникальны и информативны.
- [ ] Пустые строки вокруг заголовков, списков, таблиц, кода.
- [ ] Формат выбран по форме данных: проза / список / таблица — обоснованно.
- [ ] Перед списком есть обобщающий ключ; пункты одной структуры и длины.
- [ ] Нет двух списков подряд без прозы между ними.
- [ ] Код — в fenced-блоках с языком; inline — в бэктиках.
- [ ] Ссылки с информативным текстом, не «здесь».
- [ ] Диагональный скан за 5 секунд показывает ключевые мысли (заголовки,
      первые предложения, плашки).
