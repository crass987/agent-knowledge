# jtbd — Job (канон AJTBD) и заголовок задачи

## Overview

Два артефакта, два метода:

1. **Job-формулировка** — по канону AJTBD (Иван Замятин, Next Move Theory). Лёгкий формат: одна фраза (Level-2).
2. **Заголовок задачи / issue / PR** — название работы (что меняем). Инфостиль Ильяхова.

Общий базис — факт вместо оценки, конкретность, вычитка вслух. Стоп-слова и латиница-сканер — в `_shared/infostyle-core.md`; полный референс прозы — скилл `infostyle`.

> Канон AJTBD расходится с Christensen/Ulwick/Moesta и с памятью LLM о JTBD. Опирайтесь на канон `Next-Move-Theory-Canon/Advanced-Jobs-To-Be-Done/` (если установлен). Применяйте своими словами, не копируйте canon — лицензия CC BY-NC-SA.

## Что такое Job

Job — **спецификация желаемого перехода**: человек в ситуации А хочет оказаться в ситуации Б и выполняет переход ради Job'а уровнем выше. Единица мотивации, а не функция и не потребность.

- **Job ≠ фича.** «Хочу дашборд» — решение. Job: «хочу за один экран понять, какой сервис упал».
- **Job ≠ потребность.** «Хочу быть в курсе» — слишком абстрактно.
- **Job ≠ проблема.** Проблема — симптом (см. Job → Solution → Problem).
- **Job ≠ решение.** Формулируйте переход, который хочет человек, а не механизм: «сид-набор», «профиль», «кнопка», «настройка» — решения, не Job.

**Тест на Job:** формулировку можно закрыть другой реализацией, не вашей → это Job. Только вашей → это фича или решение.

## Когда использовать

- Сформулировать пользовательскую задачу как Job.
- Придумать или переделать заголовок задачи / issue / PR.
- Проверить чужую Job-формулировку или заголовок на прочность.

## Когда НЕ использовать

- Заголовок статьи / лендинга / анонса / релиз-нотс → `infostyle` (это польза читателю, не работа и не Job).
- Болеи и jobs из транскрипта встречи → `am-pain-mining`.
- Полная спецификация / PRD → `spec-writing` / `am-write-specs`.

## Ремесло 1. Job-формулировка (канон AJTBD, Level-2)

### Шаблон — одна фраза

> **Когда [контекст], я хочу [глагол + объект] с [критерии успеха], чтобы [ожидаемый результат Job'а уровнем выше].**

Части:

- **Когда [контекст]** — особенности человека и ситуации, из которых растут именно эти критерии. Сжато до ключевого момента (5–8 слов), на языке пользователя, не пересказ условия.
- **я хочу [глагол + объект]** — ожидаемый результат, сам переход из А в Б. Глагол-фраза (не существительное), направлен в будущее, от первого лица. Ядро Job; всё остальное — вокруг него.
- **с [критерии успеха]** — конкретные, измеримые условия «достаточно хорошо». У каждого есть направление (ось: цена / скорость / безопасность / …) и уровень (порог: «под $1800», «за 7 дней», «0 молчащих мониторов»). Без критериев Job — желание, а не спецификация.
- **чтобы [Job уровнем выше]** — ожидаемый результат Job'а, который выполняют ради него. Не польза и не выгода. Поднимает формулировку над инструментом.

### Ключевые правила канона

- **Один инфинитив — один Job.** «Хочу открыть и отфильтровать» — два Job'а, разнесите. Цепочка глаголов («правлю… хочу… чтобы…») — это стек; парсите его по уровням.
- **Тот же результат, другие критерии — другой Job.** UberX и Uber Comfort: один глагол, разные критерии, разные Job'ы.
- **Core и Big Job.** Core — что выполняет ваш продукт; Big — уровнем выше, несёт мотивацию. Поднимайтесь над инструментом к picture-level Job, не формулируйте боль или инструмент.
- **Первое лицо во всех частях.** Не смешивайте лица («когда закупщик видит… я хочу» — сбой).
- **Связка «как?».** После «хочу…» возникает «как?», на который отвечает блок «чтобы…». Разрыв — формулировка не закончена.

### Пример: плохо → хорошо

**Плохо:**
> Когда правлю дашборды под релиз, я хочу держать сиды в одном месте, чтобы было удобно и правки ловились тестом.

Решение («сиды в одном месте») вместо Job; нет критериев; «чтобы» — benefit, не высший Job; стоп-слово «удобно».

**Хорошо:**
> Когда разворачиваю AM на новом контуре, я хочу увидеть здоровье инфраструктуры на мониторинге сразу после установки — дашборды с данными контура, дефолтные мониторы, срабатывающие на реальных событиях, без ручной настройки, — чтобы с первого дня полагаться на мониторинг в защите надёжности этой инфраструктуры.

«Увидеть здоровье» — переход (Job), не механизм; критерии конкретны; «чтобы» — Job уровнем выше.

### Глубже — 8 элементов (когда нужно попасть точно)

Полный Job — восемь элементов: контекст · негативные эмоции (до) · Consideration Set · триггер · ожидаемый результат · критерии успеха · позитивные эмоции (после) · высший Job, плюс частота, бюджет, важность. Шаблон Level-2 сжимает их в одну фразу. Разворачивайте полный набор, когда точность критична (новый сегмент, цена, позиционирование) — канон в `job-structure.md`, `ajtbd-key-theses.md`.

## Job → Solution → Problem: не начинайте с проблемы

Проблема — **следствие**: она возникает, когда нанятое решение не дотягивает до критериев Job. Реконструируйте цепочку, прежде чем формулировать:

**Job** (чего хочет человек) → **Solution** (что нанял) → **Problem** (где решение не дотягивает).

Формулируйте Job, а не проблему: проблема исчезает, когда Solution выполняет Job по критериям успеха.

## Ремесло 2. Заголовок задачи / issue / PR

Заголовок задачи называет **работу** — что меняем, — а не пользу. Польза живёт в Job; заголовок говорит, **что меняется**.

- Названо действие или объект изменения: «Интерфейс списка дашбордов: фильтры, поиск и дерево папок» — что делаем.
- Не benefit-формулировка: «Найти нужный дашборд…» как `summary` — это заголовок статьи, не работы.
- «Улучшение» — не-слово. Конкретизируйте объект и действие.
- Суть — в первых словах; без канцелярита; глагол действия или существительное-объект.

| Жанр | Плохо | Хорошо |
|---|---|---|
| Задача (Jira `summary`) | Найти нужный дашборд: фильтры и поиск | Интерфейс списка дашбордов: фильтры и поиск |
| Статья / лендинг | Интерфейс списка дашбордов: … | Найти нужный дашборд среди десятков → `infostyle` |

Job-формулировка (Ремесло 1) и заголовок задачи (Ремесло 2) — разные жанры: не тяните «чтобы…» из Job в `summary`.

## Антипаттерны

| Провал | Признак | Лекарство |
|---|---|---|
| Решение вместо Job | «хочу кнопку / сид-набор / профиль» | спросить «зачем?» — дойти до перехода |
| Multi-verb stack | «правлю… хочу держать… чтобы показывали» | один глагол = один Job; распарсить стек |
| Нет критериев | «быстро», «удобно», «надёжно» | конкретные направление + уровень (цифра / срок / состояние) |
| «Чтобы» = benefit | «чтобы всё работало / ловилось тестом» | ожидаемый результат Job'а уровнем выше |
| Инструмент, не picture | сформулировали боль или механизм | подняться к Core/Big Job |
| Старт с проблемы | «у нас проблема с X» | реконструировать Job → Solution → Problem |
| Чужое определение JTBD | Christensen / Ulwick | канон AJTBD (см. Источники) |
| Смешение лиц | «когда закупщик видит… я хочу» | всё от первого лица «я» |
| Канцелярит / кальки | «в сжатые сроки», «с указанием владельцев» | вычитка вслух; глагол действия |

## Чек-лист сдачи

**Job-формулировка:**

- [ ] «Когда» — контекст, сжатый, не пересказ условия.
- [ ] «Хочу + глагол + объект» — переход, не решение; один инфинитив.
- [ ] «С критерии» — конкретные, направление + уровень.
- [ ] «Чтобы» — Job уровнем выше, не benefit.
- [ ] Первое лицо во всех частях; нет смешения лиц.
- [ ] Нет стоп-слов; латиница-сканер пройден.
- [ ] Прочитано вслух.

**Заголовок задачи:**

- [ ] Называет работу (что меняем), не пользу.
- [ ] Не «Улучшение»; объект и действие ясны с первого взгляда.
- [ ] Жанр не перепутан со статьёй.
