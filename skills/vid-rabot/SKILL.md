# vid-rabot — разметка по «Виду работ»

Классифицирует завершённые тикеты продуктового проекта по **«Виду работ»** (`customfield_22202`) — 7 значений, разнесение **CAPEX/OPEX** для МСФО.

**«Специализированная разработка»** (`customfield_33800`, Cloud/Security/AI/Platform-Ready) — *опционально*: пишется только если поле подключено к проекту. На **MON оно не подключено** (400 на запись) → **пропускаем**, классификацию сохраняем в артефакте на будущее (шаг 5 + `taxonomy.md`).

Канон правил: Confluence `DRSTAND`, pageId **322803823**. Таксономия и правила разрешения споров — в **`taxonomy.md`** (открой перед классификацией).

**Ведущий принцип:** каждое решение — это сначала **CAPEX или OPEX** (труд капитализируется в актив продукта или списывается в расход периода), потом уточняешь конкретное значение.

> Финансы. «Вид работ» кормит МСФО (CAPEX/OPEX) через Tempo — ошибка не косметика. Поэтому: верифицируй опции поля до массовой записи, показывай sanity-сэмпл, сомнительные — в ручную разметку, не угадывай.

## Параметры прогона
Уточни у пользователя, если не задано явно:
- **SCOPE** — `fixVersion = "v.X.Y.Z"` (умолчание) / `sprint = "..."` / произвольный JQL.
- **PROJECT** — по умолчанию `MON`.
- **MODE** — `write` (умолчание: авто-запись `customfield_22202`; `customfield_33800` — только если подключён к проекту) / `dry-run` (только отчёт).

## Process

### 1. Собери рабочий набор
JQL (умолчание — завершённые): `project = <PROJECT> AND <SCOPE> AND statusCategory = Done`.

**Два режима скоупа:**
- **Завершённые** (умолчание, основной кейс МСФО — что закончено): `... AND statusCategory = Done`.
- **Весь релиз / доразметка** (включая in-progress/to-do — на них тоже списывается время в Tempo; или возобновление после частичного прогона): `... AND "Вид работ" is EMPTY` — найдёт всё неразмеченное в скоупе (done + in-progress). Cancelled вычитай по `status.name`.
- ⚠ **Не фильтруй по именам статусов** (`status in ("To Release", …)`) — Jira Server валидирует их криво и кидает 400 («value does not exist») даже для валидных статусов с пробелами. Используй `statusCategory = Done`; отменённые («Cancelled», тоже done-категория) вычитай постфактум по `status.name`.
- ⚠ **`auto_paginate` часто приносит только первую страницу (~50)** — если `total` больше возвращённого, догоняй вручную через `start_at=50,100,…` минимальными полями (только ключи) и склеивай; потом вычти Cancelled.
- «Завершённые» = statusCategory Done, **кроме Cancelled** (отменённые не размечаем).
- В режиме «завершённые» (умолчание) не берём in-progress: «На тестировании», «Готово к релизу», «Регрессионное тестирование». В режиме «весь релиз» (через `is EMPTY`) in-progress/to-do входят.
- **Пропусти** Epic / «Портфель проектов» / «Бизнес-инициатива» — на них время не списывается (CAPEX/OPEX не нужен). Берём Задача / История / Ошибка / Подзадача.
- **Завершение шага:** полный список ключей собран (с ручной пагинацией, если нужно), count известен, отменённые исключены, каждый тикет в done-статусе. Покажи count и разбивку по статусам/типам.

### 2. Верифицируй опции поля на целевом проекте
Опции select-полей **зависят от field-конфигурации проекта**: один и тот же `customfield_22202` на одном проекте может иметь «Формирование статистики», на другом — стандартные 7. Сверь строки под **целевой** проект.
- Найди тикеты проекта с уже заполненным полем: `"Вид работ" is not EMPTY` — вернёт реальные option-строки этого проекта.
- `get_issue(expand=["editmeta"])` через MCP **allowedValues не отдаёт**, createmeta тоже обрезан — не трать время; только выборка заполненных тикетов или пробный write.
- Если заполненных тикетов нет — **один** пробный `update_issue` (формат `{value}`, см. шаг 5) + readback.
- **Завершение шага:** точные option-строки для `customfield_22202` и `customfield_33800` подтверждены на целевом проекте. Без этого массовую запись не начинай.

### 3. Классифицируй батчами
Тяни `batch_get_issues` по 50; поля: `summary, description, issuetype, status, labels, parent (Epic), customfield_22202, customfield_33800`. Классифицируй чанками по ~25 тикетов. При >75 — диспэтчи параллельные субагенты (`Agent` tool) по чанкам; каждый возвращает `{ключ, вид_работ, спец, confidence, основание}`.
- По каждому тикету открой **`taxonomy.md`** и пройди решение: (1) CAPEX/OPEX? (2) какое значение? + confidence + основание (одна строка).
- Драйверы решения: суть (summary + description), родительский Epic, labels. При низкой уверенности подтяни коммиты/PR (`get_development_information`) и комменты.
- **Завершение шага:** КАЖДЫЙ тикет рабочего набора имеет `вид_работ + спец + confidence + основание`. Без единого пропуска.

### 4. Sanity-гейт перед записью
Покажи пользователю ~8-10 разнородных тикетов: ключ (кликабельная ссылка), summary, предсказание обоих полей, основание. Получи «ок» → массовая запись. Это последний рубеж перед финансами.
- **Завершение шага:** пользователь подтвердил сэмпл (или поправил таксономию → тогда правишь `taxonomy.md` и перезапускаешь шаг 3).

### 5. Запиши поля
⚠ **select-кастомник пишется объектом `{"value": "..."}`**; bare-строка даёт **400** на Jira Server.

**Поля не равнозначны — проверяй редактируемость каждого на целевом проекте пробным write:**
- `customfield_22202` (Вид работ) — редактируем на MON (значения `Develop Roadmap`, `Certification`, `Internal`, `Custom Develop`, `Business Research`, `Support` подтверждены).
- `customfield_33800` (Специализированная разработка) — **на MON НЕ пишется и мы его пропускаем** (out of scope): поле не подключено к экрану проекта → 400 на любое значение. По канону (DRSTAND-322803823) подключение делается обращением на портал обращений Astra Linux. Классификацию (Cloud/AI/Security-Ready) сохраняем в артефакте; запись этого поля запускаем только после подключения.

**Массово — `bulk_update_issues`, по ОДНОМУ кастомнику за раз.** Включение в один bulk-набор нескольких кастомников (особенно нередактируемого) валит весь набор в 400. Группируй по `vid` и пиши `customfield_22202` группой (3 группы вместо 150 вызовов):
```
bulk_update_issues(issue_keys=[...группа по vid...], fields={"customfield_22202": {"value": "Develop Roadmap"}})
```
⚠ Большие наборы (~100+) на MON уходят в фон (>120 c) — bulk асинхронный, дождись результата.
- **Исключай тикеты, правленные руками** — спроси у пользователя перед записью; эти ключи выкинь (не затирать чужие правки).
- Режим `write` (по умолчанию): пишешь все, включая сомнительные (лучшей догадкой), они же дублируются в артефакт. `dry-run` — не пишешь.
- **Readback** 2-3 тикетов на значение — подтверди, что встало.
- **Завершение шага:** все группы `customfield_22202` записаны и подтверждены readback'ом; ручные правки не тронуты; нередактируемое поле отмечено (cf33800 на MON → задача на подключение через портал); сомнительные собраны отдельно.
