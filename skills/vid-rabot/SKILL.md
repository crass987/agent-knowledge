# vid-rabot — разметка по «Виду работ»

Классифицирует завершённые тикеты продуктового проекта по **«Виду работ»** (`customfield_22202`) — 7 значений, разнесение **CAPEX/OPEX** для МСФО.

**«Account»** (`customfield_13600`, плагин Tempo Accounts) — выводится **детерминированно из «Вида работ»**: CAPEX-виды (Develop Roadmap, Certification) → capex-аккаунт продукта, остальные → opex-аккаунт. Отдельной классификации НЕ требует — только механика записи (шаг 5 + таблица в `taxonomy.md`). Для MON: capex = «Astra Monitoring: capex» id **282**, opex = «Astra Monitoring: opex» id **168** (подтверждены записью 2026-08-13).

**«Специализированная разработка»** (`customfield_33800`, Cloud/Security/AI/Platform-Ready) — *опционально*: пишется только если поле подключено к проекту. На **MON оно не подключено** (400 на запись) → **пропускаем**, классификацию сохраняем в артефакте на будущее (шаг 5 + `taxonomy.md`).

Канон правил: Confluence `DRSTAND`, pageId **322803823**. Таксономия и правила разрешения споров — в **`taxonomy.md`** (открой перед классификацией).

**Ведущий принцип:** каждое решение — это сначала **CAPEX или OPEX** (труд капитализируется в актив продукта или списывается в расход периода), потом уточняешь конкретное значение. **Развилка CAPEX/OPEX без решающего сигнала → CAPEX** (решение команды 2026-08-13, см. `taxonomy.md` → Решения команды).

> Финансы. «Вид работ» кормит МСФО (CAPEX/OPEX) через Tempo — ошибка не косметика. Поэтому: верифицируй опции поля до массовой записи, показывай sanity-сэмпл, сомнительные — в ручную разметку, не угадывай.

## Параметры прогона
Уточни у пользователя, если не задано явно:
- **SCOPE** — `since-last` (умолчание, см. ниже) / `fixVersion = "v.X.Y.Z"` / `sprint = "..."` / произвольный JQL.

**SCOPE `since-last` — разметка «с последнего раза» (правило 2026-09-08).** По умолчанию размечаем **все задачи, по которым время списано после предыдущего прогона**, — так в выборку попадают и новые, и опоздавшие, и выпавшие из спринта/релиза тикеты. Дата-время предыдущей разметки хранится в **`last-run.txt`** рядом со скиллом (одна строка: ISO-время окончания массовой записи + скоуп; файл ведёт сам скилл). Механика:
1. Прочитай `last-run.txt`; если файла нет — это первый прогон, спроси скоуп у пользователя и после прогона создай файл.
2. Выборка: `project = <PROJECT> AND worklogDate >= "<last-run>" AND "Вид работ" is EMPTY` (+ режим «завершённые»: `AND statusCategory = Done`). worklogDate берёт по факту списания в Tempo — бэкфиллы задним числом тоже ловятся (см. pitfall про retro-backfill в learnings).
3. **Записывай в `last-run.txt` в конце шага 5** (после успешной массовой записи и readback) — момент окончания записи, не начала: всё, что списано позже, уйдёт в следующий прогон.
4. Дельта-прогон по Tempo-выгрузке (список тикетов «Не указан аккаунт и вид работ») — тот же принцип: сверь выгрузку с текущим Jira-состоянием (выгрузка почти всегда устаревает), разметь только реально неразмеченные.
- **PROJECT** — по умолчанию `MON`.
- **MODE** — `write` (умолчание: авто-запись `customfield_22202` + `customfield_13600`; `customfield_33800` — только если подключён к проекту) / `dry-run` (только отчёт).
- **Доразметка Account** (отдельный кейс): «Вид работ» уже стоит, надо докатать только Account — JQL `project = <PROJECT> AND "Вид работ" is not EMPTY AND "Account" is EMPTY`, классификация не нужна, сразу шаг 5 (две bulk-группы по таблице из `taxonomy.md`).

## Process

### 1. Собери рабочий набор
JQL (умолчание — завершённые): `project = <PROJECT> AND <SCOPE> AND statusCategory = Done`.

**Два режима скоупа:**
- **Завершённые** (умолчание, основной кейс МСФО — что закончено): `... AND statusCategory = Done`.
- **Весь релиз / доразметка** (включая in-progress/to-do — на них тоже списывается время в Tempo; или возобновление после частичного прогона): `... AND "Вид работ" is EMPTY` — найдёт всё неразмеченное в скоупе (done + in-progress).
- ⚠ **Не фильтруй по именам статусов** (`status in ("To Release", …)`) — Jira Server валидирует их криво и кидает 400 («value does not exist») даже для валидных статусов с пробелами. Используй `statusCategory = Done`.
- ⚠ **`auto_paginate` часто приносит только первую страницу (~50)** — если `total` больше возвращённого, догоняй вручную через `start_at=50,100,…` минимальными полями (только ключи) и склеивай.
- **Cancelled размечаем** (решение владельца 2026-09-08, MON): время по отменённым тоже списано в Tempo — классифицируй по сути работ, как живые тикеты, и пиши поля. Тикеты с label `cancelled`, но статусом Done — тем более.
- В режиме «завершённые» (умолчание) не берём in-progress: «На тестировании», «Готово к релизу», «Регрессионное тестирование». В режиме «весь релиз» (через `is EMPTY`) in-progress/to-do входят.
- **Пропусти** Epic / «Портфель проектов» / «Бизнес-инициатива» — на них время не списывается (CAPEX/OPEX не нужен). Берём Задача / История / Ошибка / Подзадача.
- **Завершение шага:** полный список ключей собран (с ручной пагинацией, если нужно), count известен, отменённые исключены, каждый тикет в done-статусе. Покажи count и разбивку по статусам/типам.

### 2. Верифицируй опции поля на целевом проекте
Опции select-полей **зависят от field-конфигурации проекта**: один и тот же `customfield_22202` на одном проекте может иметь «Формирование статистики», на другом — стандартные 7. Сверь строки под **целевой** проект.
- Найди тикеты проекта с уже заполненным полем: `"Вид работ" is not EMPTY` — вернёт реальные option-строки этого проекта.
- **Быстрый путь (после креатемета-раунда jira-mcp 2026-09-17):** `get_create_meta(project_key, issue_type)` отдаёт allowedValues на MON (live-verified: 22202 — 7 опций, 22100 — 14). Начинай с него.
- `get_issue(expand=["editmeta"])` через MCP allowedValues не отдаёт.
- Если `get_create_meta` вернул пусто или упал — фолбэк: выборка заполненных тикетов или один пробный write.
- Если заполненных тикетов нет — **один** пробный `update_issue` (формат `{value}`, см. шаг 5) + readback.
- Для `customfield_13600` сверь id обоих Tempo-аккаунтов продукта с `taxonomy.md` (MON: capex 282 / opex 168). ID смотрятся в Tempo (Jira → Apps → Tempo → Accounts) или спрашиваются у пользователя. ⚠ JQL `"Account" = "<KEY>"` для проверки существования бесполезен — несуществующие ключи молча дают 0.
- **Завершение шага:** точные option-строки для `customfield_22202` и `customfield_33800` + id обоих Tempo-аккаунтов подтверждены на целевом проекте. Без этого массовую запись не начинай.

### 3. Классифицируй батчами
Тяни `batch_get_issues` по 50; поля: `summary, description, issuetype, status, labels, parent (Epic), customfield_22202, customfield_33800`. Классифицируй чанками по ~25 тикетов. При >75 — диспэтчи параллельные субагенты (`Agent` tool) по чанкам; каждый возвращает `{ключ, вид_работ, спец, confidence, основание}`.
- По каждому тикету открой **`taxonomy.md`** и пройди решение: (1) CAPEX/OPEX? (2) какое значение? + confidence + основание (одна строка).
- Драйверы решения: суть (summary + description), родительский Epic, labels. При низкой уверенности подтяни коммиты/PR (`get_development_information`) и комменты.
- **Завершение шага:** КАЖДЫЙ тикет рабочего набора имеет `вид_работ + спец + confidence + основание`. Без единого пропуска.

### 4. Sanity-гейт перед записью
Покажи пользователю ~8-10 разнородных тикетов: ключ (кликабельная ссылка), summary, предсказание полей (вид работ + спец; Account выводится из вида работ — отдельного решения не требует), основание. Получи «ок» → массовая запись. Это последний рубеж перед финансами.
- **Завершение шага:** пользователь подтвердил сэмпл (или поправил таксономию → тогда правишь `taxonomy.md` и перезапускаешь шаг 3).

### 5. Запиши поля
⚠ **select-кастомник пишется объектом `{"value": "..."}`**; bare-строка даёт **400** на Jira Server.

**Поля не равнозначны — проверяй редактируемость каждого на целевом проекте пробным write:**
- `customfield_22202` (Вид работ) — редактируем на MON (значения `Develop Roadmap`, `Certification`, `Internal`, `Custom Develop`, `Business Research`, `Support` подтверждены).
- `customfield_33800` (Специализированная разработка) — **на MON НЕ пишется и мы его пропускаем** (out of scope): поле не подключено к экрану проекта → 400 на любое значение. По канону (DRSTAND-322803823) подключение делается обращением на портал обращений Astra Linux. Классификацию (Cloud/AI/Security-Ready) сохраняем в артефакте; запись этого поля запускаем только после подключения.

**Массово — `bulk_update_issues`, по ОДНОМУ кастомнику за раз.** Включение в один bulk-набор нескольких кастомников (особенно нередактируемого) валит весь набор в 400. Группируй по `vid` и пиши `customfield_22202` группой (3 группы вместо 150 вызовов):
```
bulk_update_issues(issue_keys=[...группа по vid...], fields={"customfield_22202": {"value": "Develop Roadmap"}})
```
⚠ Большие наборы (~100+) на MON уходят в фон (>120 c) — bulk асинхронный, дождись результата. Пока крутится длинный bulk-цикл, MCP-сервер насыщается — даже чтения уходят в очередь/фон; прогресс проверяй отдельным подключением (`jira_client` + его `.env`, креды не извлекать) или просто дождись уведомления.

**Account (`customfield_13600`) — сразу после `customfield_22202`, двумя группами** (CAPEX-виды / OPEX-виды по таблице из `taxonomy.md`; для MON — `"282"` / `"168"`):
```
bulk_update_issues(issue_keys=[...capex-виды...], fields={"customfield_13600": "282"})
bulk_update_issues(issue_keys=[...opex-виды...],  fields={"customfield_13600": "168"})
```
- ⚠ **Tempo-аккаунт пишется ТОЛЬКО bare-строкой с id** (`"168"`). Объект `{"id": N}`, `{"value": …}`, bare-int — всё даёт 400 **«Account id 'null' is invalid»** (проверено 2026-08-13 на всех вариантах).
- ⚠ **MCP может соврать про 401.** Маппинг ошибок сервера ловит подстроку `"401"` — ключ тикета вроде MON-**4013** превращает реальный 400 в «Ошибка аутентификации: проверьте JIRA_API_TOKEN». Не чини креды — смотри настоящий статус в `~/.cache/jira-mcp/logs/mcp-<дата>.jsonl`.
- Readback показывает объект целиком (`id`, `key`, `name`) — сверяй `key`: `ASMON-CAPEX` / `ASMON-OPEX`.
- **Исключай тикеты, правленные руками** — спроси у пользователя перед записью; эти ключи выкинь (не затирать чужие правки).
- Режим `write` (по умолчанию): пишешь все, включая сомнительные (лучшей догадкой), они же дублируются в артефакт. `dry-run` — не пишешь.
- **Readback** 2-3 тикетов на значение — подтверди, что встало.
- ⚠ Сбой `Read timed out` у одного тикета в bulk не значит «не записалось» — проверь readback'ом; чаще значение уже стоит (таймаут был на чтении ответа).
- ⚠ **Большой bulk (50+ ключей): MCP абортирует вызов по idle-timeout (1800 с), но Jira Server доводит операцию сам** (~45 мин на 265 обновлений, темп растёт). Не перезапускай — полли прогресс прямым PAT-подключением (`key in (...) AND "Вид работ" is EMPTY`) раз в 5-7 мин до нуля. Мелкие bulk в это время тоже висят в фоне; одиночный `update_issue` проходит мгновенно.
- **Завершение шага:** все группы `customfield_22202` и `customfield_13600` записаны и подтверждены readback'ом; ручные правки не тронуты; нередактируемое поле отмечено (cf33800 на MON → задача на подключение через портал); сомнительные собраны отдельно. **Если SCOPE = `since-last` — обнови `last-run.txt`** (ISO-время окончания записи + скоуп).

### 5.5. Финальная сверка скоупа (обязательный шаг, после записи)

Скоуп снапшотится в момент сбора, а тикеты заводят и двигают в спринт постоянно — за время прогона (1-3 ч) выпадают новички (кейс 2026-09-08: MON-5011/5012/5013). Перед завершением:

1. Перечитай исходный JQL скоупа ещё раз (`"Вид работ" is EMPTY` вернёт только новых пропущенных).
2. Новых тикетов, попавших в скоуп после сбора, — классифицируй и дозапиши (они малочисленны, классифицируй сам, без субагентов).
3. Сверь счётчики: собрано N, классифицировано N, записано N; расхождения объясни поимённо.
4. Для MONEY-арбитража используй Tempo-отчёт «Не указан аккаунт и вид работ» — он показывает фактические дыры, которые JQL не видит (тикеты вне спринта, опоздавшие worklog-и). Сверка выгрузки с Jira почти всегда показывает, что выгрузка устарела, — сравнивай с текущим состоянием, а не переписывай поверх разметки.
